# Upload d'images (Cloudflare R2)

Les images (photos produit, logos) sont televerses **directement du navigateur vers R2**
via une URL presignee. Le serveur applicatif ne recoit jamais les octets : il verifie
les droits, le type et la taille annonces, puis signe une URL valable 5 minutes.

Sans configuration R2, les champs image retombent sur la saisie manuelle d'une URL.
L'application reste donc fonctionnelle avant cette configuration.

## 1. Creer le bucket

Tableau de bord Cloudflare > R2 > **Create bucket**. Note son nom : c'est `R2_BUCKET`.

## 2. Creer un jeton d'API

R2 > **Manage R2 API Tokens** > Create API token, permission **Object Read & Write**,
limite au bucket cree.

Cloudflare affiche alors :

- **Access Key ID** -> `R2_ACCESS_KEY_ID`
- **Secret Access Key** -> `R2_SECRET_ACCESS_KEY` (affiche une seule fois)

L'**Account ID** se trouve en haut a droite du tableau de bord R2 -> `R2_ACCOUNT_ID`.

## 3. Rendre le bucket lisible publiquement

Les images doivent etre servies aux navigateurs. Dans le bucket > Settings > **Public access** :

- soit activer le domaine de dev **r2.dev** (pratique pour demarrer, non destine a la production) ;
- soit brancher un **domaine personnalise** (recommande : `cdn.exemple.com`).

L'URL obtenue, **sans slash final**, est `R2_PUBLIC_BASE_URL`. Exemples :

```
R2_PUBLIC_BASE_URL="https://pub-xxxxxxxxxxxx.r2.dev"
R2_PUBLIC_BASE_URL="https://cdn.exemple.com"
```

> Seul l'acces en **lecture** est public. L'ecriture reste impossible sans une URL
> signee par le serveur.

## 4. Autoriser le CORS

C'est l'etape qu'on oublie : le navigateur envoie le fichier vers un autre domaine
que celui de l'application, R2 doit donc l'autoriser explicitement. Sans cela, l'upload
echoue avec une erreur CORS dans la console, alors que la signature est valide.

Bucket > Settings > **CORS policy** > Add CORS policy :

```json
[
  {
    "AllowedOrigins": [
      "http://localhost:3000",
      "https://app.exemple.com"
    ],
    "AllowedMethods": ["PUT"],
    "AllowedHeaders": ["content-type"],
    "MaxAgeSeconds": 3600
  }
]
```

Remplace `https://app.exemple.com` par l'origine reelle de l'application. Chaque origine
qui televerse doit figurer dans la liste (dev, preproduction, production).

## 5. Renseigner l'environnement

```
R2_ACCOUNT_ID="..."
R2_ACCESS_KEY_ID="..."
R2_SECRET_ACCESS_KEY="..."
R2_BUCKET="..."
R2_PUBLIC_BASE_URL="https://..."
```

Redemarre le serveur : les champs image affichent alors un bouton d'upload a la place
du champ URL.

## Comment c'est construit

- `src/server/storage.ts` : signature des URL (aws4fetch, SigV4), controle des droits
  via `requireCompanyAccess`, allowlist de types et limite de taille.
- `src/components/ImageUploadField.tsx` : champ reutilisable (apercu, remplacement,
  retrait), avec repli sur la saisie d'URL si R2 n'est pas configure.

Points de conception a connaitre :

- **Le SVG est refuse.** Un SVG peut embarquer du script et serait servi depuis le
  domaine public du bucket. Types acceptes : JPEG, PNG, WEBP, GIF, AVIF.
- **Taille maximale : 5 Mo** (`maxUploadBytes` dans `storage.ts`).
- **Le Content-Type est signe.** Le PUT doit envoyer exactement le type annonce au
  serveur, sinon R2 rejette la requete : on ne peut pas faire valider un JPEG puis
  televerser autre chose.
- **Les cles sont prefixees par entreprise** (`companies/<companyId>/<kind>/<uuid>.<ext>`).
  Le nom du fichier d'origine n'est jamais utilise.
- **Les images remplacees ne sont pas supprimees** de R2 : changer un logo laisse
  l'ancien objet en place. Prevoir une regle de cycle de vie sur le bucket, ou un
  menage, si le volume devient un sujet.
